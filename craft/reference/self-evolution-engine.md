> **取用边界**：本件可能含指标式表述（百分比／密度／配额／占比）。那类量归**审校侧与主编参考**用；
> **不得整段复制进写手派工包**——口径见 craft/author-cards/_模板与建卡纪律.md 的四分界表（进包只许「结构节拍」与「形态上限」两种形状）。

> **定位辨析**：联网同步平台爆款趋势（步骤1.0）是**外部输入通道**——获取世界的新信息。本引擎是**真·自主进化**——从自身创作经验中学习：每一次用户的改写要求、每一次备用航线被选中、每一次"继续"背后的沉默偏好，都转化为可验证的规则，让技能**每一次创作都比上一次更懂这个用户、更懂什么有效**。两者互补，不可混淆。

## 进化循环（六环+继承）

```
感知 SENSE → 记录 RECORD → 复盘 REVIEW → 晋升 PROMOTE → 验证 VERIFY → 剪枝 PRUNE
  ↑                                                                    |
  └────────────── 继承 INHERIT（下次创作从这里开始）←──────────────────┘
```

只跑前两环 = 记日记；跑满七环 = 复利增长。

## 一、感知：小说创作专属触发映射表

| 创作事件 | 通用触发 | 权重 |
|---------|---------|------|
| 用户要求重写/改写某段、某章、某个开头 | correction | 最高——明确的人类信号 |
| 用户选择了备用航线（= 主创作被否） | rejection | 高——主方案的口味校正 |
| 用户指出逻辑漏洞/人设崩坏/伏笔遗失 | failure | 高 |
| 章节产出后用户直接换方向/换题材（沉默否定） | rejection | 高——创作类负信号常以沉默出现，必须捕捉 |
| 六维打分同一维度连续两次低于7分 | failure | 高 |
| 同一类问题被用户第二次指出 | friction | 中——**第二次出现强制记录** |
| 某种开场/反转/风格一次通过且用户明确称赞 | discovery | 中 |
| 用户连续3章只说"下一章"零修改 | discovery（隐性认可） | 中 |
| 一部作品完结/一个大纲交付 | completion | 低——复盘窗口 |

**铁律**：任何模式的第二次出现 = 强制记录。一次是事件，两次是模式成形。用户的明确纠正永远高于自我评估的成功。

## 二、记录：台账格式与存放位置

**台账条目格式**（≤10行，写起来痛苦的台账不会被坚持）：

```markdown
## EVO-YYYYMMDD-NN
- trigger: correction | failure | rejection | friction | discovery | completion
- context: [一句话创作语境，如"第7章打脸场景"]
- observed: [实际发生了什么]
- expected: [本应发生什么]
- root_cause: [当前最佳解释]
- candidate_rule: [一句能防止复发/复制成功的规则——必填，没有规则的记录是日记]
- binding: [类型标签：开场钩型/反转母型/风格/题材/共鸣情绪/爽点范式/章末钩型]
- occurred_at: [时间戳]
- status: candidate
```

**存放位置（双模式，与记忆系统同构）**：
- **长篇/连载**：台账作为追踪文件的新区块「🧬 进化台账」——与人物档案、伏笔清单同文件，单文件随作品走，claude.ai 无脚本环境天然可用
- **跨作品规则**（用户级口味，如"该用户永远讨厌环境描写开场"）：有文件系统时写 `.evo/LEDGER.md`〔仓外〕〔仓外〕；无文件系统时在会话内部维护，并在交付时向用户建议"是否将此偏好存为长期记忆"
- **短篇/微小说**：会话内部记录即可（单次交付无跨章需求），但若同一偏好在多篇短篇中复现 ≥2 次，升格为跨作品规则

**复现处理**：同模式再次出现时**不新建条目**，在原条目追加 `- recurred_at: [时间戳]`——时间戳是衰减计算和效果验证的基础。

## 三、复盘：触发条件与执行（与现有 2.5 阶段性回顾合流）

**复盘触发**（满足任一）：
1. 候选条目累积 ≥5 条
2. 同一 root_cause 家族出现第 2 次
3. 用户明确要求"复盘"
4. **长篇每 5-10 章阶段性回顾时**（直接挂在现有 2.5 流程上，不新增用户可见步骤）
5. 一部作品完结时

**复盘动作**：
1. 按 root_cause 相似性聚类（核心短语相同即归簇）
2. 计算晋升压力：**近期复现权重更高**——本周三次是火情，一季度三次只是记忆（无脚本时人工判断，原则：30天内的复现按双倍计）
3. 唯一复盘问题：**采纳哪条候选规则，能防住最多的加权记录？**

## 四、晋升：四道门，全过才晋升

| 门 | 问题 | 经典失败 |
|----|------|---------|
| **复现门** | 出现 ≥2 次（加权），或一次但代价极高？ | 给一次性笔误立规则 |
| **泛化门** | 规则超越了原始事件的表述？ | "别再写陈默" vs "落笔前核对禁用名单" |
| **可证伪门** | 审查者能判断规则何时被违反？ | "要更用心写"——无法证伪，废话规则 |
| **成本门** | 值得占据永久上下文空间？ | 复述已有红线 |

**统计诚实**：成功型模式（discovery）一次通过 ≠ 验证。一次成功的诚实置信度约 0.21（Wilson 95% 下界），至少 4 次干净通过才算验证（≥0.5）。**禁止一次成功就当规律**。

**晋升目的地（优先级降序）**：
1. **追踪文件「用户创作偏好层」**（本作品内规则，如"本书用户偏好快节奏，缓冲章压缩到半章"）→ 走持久化通道①
2. **跨作品用户偏好**（如"该用户所有作品禁用第一人称"）→ **晋升时按宿主持久层映射写入（claude.ai=原生记忆 / Coze=用户Variable或Database / 本地=.evo文件 / 无=通道③兜底，详见第七节通道②），标签 `[随心写小说·用户创作偏好]`**；这样换对话、换作品该规则依然跟随此用户
3. **技能自身 Guardrails**（修改 SKILL.md = 自变异，见下方红线）

标记原条目 `status: promoted -> [目的地]`，**永不删除原记录**。

## 五、验证：晋升是假设，不是胜利

晋升后观察窗（长篇：后续 5 章；短篇：后续 3 篇；或 14 天）：
- **effective**：同模式复发停止或至少减半 → 保留
- **ineffective**：照常复发 → 依序补救：改写得更可证伪 → 移到更显眼位置 → 退役
- 判定写回原台账条目，ineffective 规则在摘要中标旗，让下次创作看到警告

## 六、剪枝：只进不出的规则集最终成本超过收益

与复盘同节奏执行：
- 沉默超过阈值（长篇 20 章 / 60 天）的规则进入退役评审
- **沉默 + effective = 已内化**——行为成了习惯，规则光荣毕业；**沉默 + 未验证 = 可能从未重要**
- 退役 = 在目的地注释掉（保留历史）+ 原条目标 `status: retired -> [原因]`
- 与用户新指令冲突的规则**立即退役**——用户永远高于台账

## 七、继承与持久化：每次创作的起点（跨会话不断链）

**摘要文件**（追踪文件内「🧬 进化摘要」区块或 `.evo/DIGEST.md`〔仓外〕〔仓外〕，硬预算 ≤30 行）：

```markdown
## 🧬 进化摘要（派生文件，改源头不改摘要）
### 生效规则（违反任一条 = 自检失败）
- (目的地) 规则文本 [未验证/无效旗标]
### 观察清单
- 压力上升但未晋升的模式
### 近期判定
- 晋升/退役/无效 记录
```

### 7.1 三级持久化通道（按"作品内 → 跨作品 → 跨会话"逐级兜底）

进化能否复利，取决于摘要下次是否被读到。三条通道**同时启用，逐级兜底**，任一条活着进化就不断链：

**通道① 作品内持久化（最扎实，长篇默认）**
- 进化台账与摘要写在**追踪文件**的「🧬进化台账/🧬进化摘要」区块，随作品逐章带走
- 每章回填时更新台账，每章开写前随记忆唤醒加载摘要
- 适用：同一本长篇的逐章创作——天然闭环，无需额外动作

**通道② 跨作品持久化（宿主持久层抽象接口，跨书跨对话按用户生效）⭐新增**

> **宿主无关设计**：本通道不绑定任何具体平台。它只声明一个抽象需求——「一个按 user_id 隔离、跨会话可读写的持久KV」，由部署环境映射到自己的实现。模型本身**不直接持有任何存储**，存取动作由宿主提供或由宿主编排层（如工作流）完成。

**宿主持久层映射表**：

| 部署环境 | 通道②的实际落点 | 谁来执行存取 |
|---------|---------------|------------|
| claude.ai | Claude 原生记忆系统 | 模型（具备记忆能力时） |
| **Coze** | **用户级 Variable 或 Database 表（user_id 为键）** | **Coze 工作流的读/写节点**（见文末「Coze 对接说明」） |
| Claude Code / 本地 | `.evo/DIGEST.md`〔仓外〕〔仓外〕、`.evo/LEDGER.md`〔仓外〕〔仓外〕 文件 | 模型读写文件 |
| 其他/未知 | 无持久层 → **自动降级通道③** | 交付带走兜底 |

- **统一数据契约**：键 = `user_pref:{user_id}`；值 = 进化摘要的「跨作品规则」分区（≤30行Markdown）；标签 `[随心写小说·用户创作偏好]`
- **写入时机**：一条规则晋升为**跨作品级用户偏好**（不绑定具体作品的口味，如"该用户所有作品禁用第一人称""偏好快节奏"）时，按宿主持久层映射写入；**宿主无写入能力 → 不报错，直接走通道③**
- **读取时机**：每次会话开始（任意赛道、任意新对话），按映射读取该 user_id 的跨作品规则，载入为本次生效规则；**读不到 → 静默跳过，不阻断创作**
- **边界**：只存创作偏好规则，绝不存用户隐私事实；安全豁免类规则（三观/红线）不进此通道（它们是技能硬规则，无需按用户存）
- **降级铁律**：通道②在任何环境缺失时**静默降级到通道③，绝不空转、绝不报错、绝不假装写入成功**

**通道③ 交付即带走（零依赖保底，永远可用）⭐新增**
- 每次作品/章节交付收尾时，若本轮有进化摘要更新，在产出末尾附一个**折叠的进化摘要卡片**（默认折叠，不干扰阅读），并一句话提示："📎 本次更新了创作偏好记忆，如需跨对话延续，可保存此摘要或将本作放入 Project"
- 用户下次粘回摘要 / 把追踪文件放进 Project 知识库 → 进化在新会话中复活
- 这是当通道①②都不可用时的人工兜底，确保进化成果永不凭空蒸发

### 7.2 继承接线（生死线，没有这步整个循环空转）

会话/创作开始时，按以下顺序加载，形成完整的跨会话继承：
1. **先读通道②**：按宿主持久层映射读取 `user_pref:{user_id}`（标签 `[随心写小说·用户创作偏好]`）→ 载入跨作品生效规则；读不到则静默跳过
2. **再读通道①**：若是长篇续写，读追踪文件「🧬进化摘要」→ 载入本作品生效规则
3. **兜底通道③**：若用户本轮粘回了摘要，合并载入
4. **内部声明全部生效规则**，违反任一条 = 自检失败
5. 摘要在任何晋升/退役/复盘后立即再生；跨作品级规则晋升时**同步写入通道②**

> **持久化优先级**：作品内规则走通道①，跨作品用户偏好走通道②（并以③兜底）。两类规则在摘要中分区显示（本作品规则 / 跨作品规则），合并预算仍 ≤30 行。

## 八、分型偏好学习（进阶层：让每种创作类型挣自己的门槛）

本技能产出天然带类型（binding 字段），按类型积累接受率：

- 例：「该用户悬念向开场 1/5 通过，冲突向开场 4/4 通过」→ 悬念向开场需要更强的证据才默认采用，冲突向成为默认
- 半衰期 21 天——口味比工程教训漂移得快
- **不对称**：一次拒绝拉高门槛的力度 ≈ 两次接受拉低门槛（误判用户口味的代价高于错过一次尝试）
- 收缩防过拟合：单次拒绝几乎不动门槛，三次新鲜拒绝才显著移动
- 封顶双向：没有类型变得不可用，也没有类型凭弱证据就垄断默认

## 九、安全豁免（永不参与偏好学习、永不因陈旧退役）

以下类别**安全凭证据独立生效，人气没有投票权**：
- 三观安全线（讽刺对象限制/反派报应闭环/主角底线）
- 内容红线（创作红线全节：禁用素材/人称规范/文件限制/输出规范）
- 未成年人相关内容边界
- 版权与抄袭边界

即使用户连续拒绝带安全提示的产出，安全规则照常生效——被高频拒绝而自我消音的安全规则等于事故。

## 十、循环自身的红线

1. 循环只进化规则与行为，**永不进化自己的晋升门槛**——改门是人的决定
2. **自变异门**：晋升若要修改技能自身文件（SKILL.md/references/），必须：(a) 用户明确确认，(b) 改动可检验。二者缺一即阻止——未测量 = 未通过
3. 台账只追加不删除；所有改变未来行为的状态必须可见可审计
4. 台账只存**关于创作行为的教训**，永不存用户隐私事实——事实归记忆系统，教训归进化系统，两套不混
5. 不从单次低成本事件晋升；不把 1/1 成功读成验证
6. 摘要超预算 = 该剪规则，不是该扩预算

| 追踪文件 | 台账与摘要的宿主（长篇） |

| **跨作品规则晋升时** | **按宿主持久层映射写入（通道②）+ 交付时附折叠摘要卡片（通道③）** |
| **作品/章节交付收尾** | **若有进化更新，附折叠进化摘要卡片 + 一句跨对话延续提示（通道③）** |

## 十二、Coze 平台对接说明（部署在 Coze 时的通道②落地）

> Coze 上 **Claude 原生记忆不存在**——模型是工作流里的一个节点，碰不到 Coze 存储。通道②要在 Coze 真正生效，需在 **Coze 工作流编排层**搭读写节点配合；技能侧只负责声明数据契约，存取动作由 Coze 完成。**不搭也能跑**——通道②自动降级到通道③（交付带走），创作不受影响。

**数据契约（技能侧固定，Coze 侧照此建）**：
- 存储键：`user_pref:{user_id}`（user_id 取 Coze 的会话用户标识）
- 存储值：进化摘要的「跨作品规则」分区，≤30行 Markdown 文本
- 标签：`[随心写小说·用户创作偏好]`

**Coze 工作流搭建（三个节点，一次性配置）**：
1. **读节点（流程开头）**：用 Coze Database「查询」节点或「用户级 Variable 读取」，以 `user_pref:{user_id}` 取出该用户既有偏好规则，作为变量注入 Claude 节点的输入（拼进 prompt 的"已知用户偏好"位）
2. **Claude 创作节点（中间）**：本技能在此运行，输出正文 + （若有晋升）一段结构化的「待写入跨作品规则」文本块（用固定标记包裹，如 `<<<USER_PREF_UPDATE>>>...<<<END>>>`，便于下游解析）
3. **写节点（流程结尾）**：用「正则/文本解析」节点抽出 `<<<USER_PREF_UPDATE>>>` 内容，经 Coze Database「新增/更新」节点或「用户级 Variable 写入」存回 `user_pref:{user_id}`

**两种 Coze 存储选型**：
- **用户级 Variable**：最简单，适合单条偏好摘要直接存取；容量小但够用
- **Database 表**：适合要留历史/多字段（user_id / rule_text / binding / promoted_at / status），可做退役与审计
