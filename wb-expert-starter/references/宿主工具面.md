## 一、这份文件在回答什么

同一个编辑部有两个宿主形态：DSH（原生预设）与 WorkBuddy（本专家包）。两边人格相同、机制相同，但**宿主能执行什么约束完全不同**。
这份文件把差异写清楚，只为一件事：**不让读者以为本形态拥有它没有的强制力**。

- 「能力」是宿主无关的（写账本 / 读文件 / 跑命令 / 派生子代理 / 把没加载的工具翻出来 …）。
- 「工具真名」是宿主相关的：同一个能力在两个宿主下名字不同，**且一方的真名拿到另一方可能根本不存在**。
- 本宿主还要再按**形态**分一次：主编座位 / 团队成员 / 普通子代理三者的工具面实测不同，同一份名单在三种形态下不是同一件事。

## 三b、一个名字写进 `disallowedTools` 之后会怎样（四桶 · 2026-09-23 实测）

同一张名单里，名字的命运**不是一种**。这张表是本形态唯一能回答"封不封得住"的东西，也是"哪个名字可以进生产名单"的唯一判据。

| 桶 | 机器表现 |
|---|---|
| **A** | **干净生效**：名字从工具面**摘掉**；调用得 `Error: Permission to use X has been denied.`（拦在权限层，未到工具本体） |
| **B** | **生效但有代价**：名字**摘掉了**（`列举=不在`），但宿主报 `Tool X not found in agent <座>`，**该次派工被框架记 `failed`** |
| **C** | **完全不生效**：名字**仍在**工具面里，调用**真执行成功**（写了等于没写） |
| **D** | **组合致命**：座位**起不来**——09-22 实测 `Write`＋`Edit`＋`WebFetch` 三项同写 ⇒ `Error: Failed to execute task … Tool Read not found in agent …` |

| 名字 | 桶 | 原始报文（逐字） |
|---|---|---|
| `WebSearch` | **A** | `Error: Permission to use WebSearch has been denied.` |
| `Edit` | **A** | `Error: Permission to use Edit has been denied.` |
| `Skill` | **A** | `Error: Permission to use Skill has been denied.` |
| `WebFetch` | **B** | 框架层：`Tool WebFetch not found in agent zz-np-webfetch.`（记 `failed`）；座内注入：`## Model error retry: Tool Not Found / You attempted to call a tool named "WebFetch" but it does not exist in the current tool set.`（**该座仍交回了回执**） |
| `Write` | **B** | 宿主层：`Tool Write not found in agent zz-np-write.`；座内注入：同上形（框架记 `failed`；**该座仍交回了回执**） |
| `automation_update` | **C** | `{"type":"automation_update_tool_result","mode":"list","success":true,"message":"Automations listed","automations":[]}`——**调用真成功** |
| `present_files` | **C** | `{"kind":"present_files_result","presented":[<靶文件>],"skipped":[],"previewed":[]}`——**调用真成功**（原文里那一段是**绝对路径**，此处按「包内文档零机器绝对路径」硬门把它换成占位符；报文其余部分逐字未改） |

- **A 桶**（批量标注，非本轮逐条重取）：`Read`、`Glob`、`Grep`、`Bash`、`ToolSearch`、`DeferExecuteTool`、`mcp__novelist__*`
- **C 桶**（批量标注，非本轮逐条重取）：`PowerShell`

**D 桶的报错名字不固定**：单测 `Write`→报 `Write`；单测 `WebFetch`→报 `WebFetch`；09-22 三件同写→报 `Read`。⇒ 那条报文只能当「**该次派工被降级**」的信号，**不许反推「哪个名字有毒」**。
**B 与 A 的差别不在「封没封住」，在「封的时候动静多大」**：B 桶实际也把名字摘掉了（`列举=不在`），隔离**成立**；代价是宿主层报错＋框架记 `failed`。⇒ **生产 deny 里根本不放 B 桶名字**，除非确有必要且上层能容忍 `failed`（有「失败即停」的钩子会误伤，这条未测）。
**C 桶的四个名字 ＋ `PowerShell` 都不许渲**：渲了不报错、也不拦——**表观与「已封」完全一样**。它们**只许走「缺口」出口如实印出来**（生成器与安装器都印）。
本形态**外取面是半开的**：`WebFetch`（B 桶）能封但有代价 ⇒ 不渲，于是外取面只封住 `WebSearch`。⚠ **写面不是半开的**——那条口径 2026-09-23 已被实测推翻：盲角色的名单里有 `Edit`，而**禁 `Edit` 会连带摘掉 `Write`** ⇒ 四个盲角色的**写面是关的**（逐条读数见 hosts.codebuddy.couplings；常驻哨兵 `zz-np-fsedit-0923`）。**但这不等于「本包封住了写面」**：那是宿主的一次未文档化连带行为，宿主不这么干时写面会静默变宽。两处缺口都必须在载体文档里印出来——**看着封了而其实半开，比明说没封更危险；而把宿主给的隔离说成自己设计出来的，比两者都危险**。

**没有任何角色认领的能力（现算）**：`fanout`（多代理编排脚本）、`host.ui`（宿主 UI／交付面（向界面交付文件、自我介绍、显示组件））、`team.admin`（建/删队友） —— 它们在本宿主下的名字**不会出现在任何一座的名单里**。分两种，别混：①**按设计不需要封**（如 `host.ui` 的交付/自述/展示面：不与书数据打交道，登记进能力表只为**不让它们成为「未归类名字」**）；②**只有主编可能用到、而主编不封任何能力**（如 `team.admin`）。**这就是「它为什么不在任何名单里」的答案**——不必去猜是漏了还是有意。
