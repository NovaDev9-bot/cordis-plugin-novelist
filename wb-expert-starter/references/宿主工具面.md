## 一、这份文件在回答什么

同一个编辑部有两个宿主形态：DSH（原生预设）与 WorkBuddy（本专家包）。两边人格相同、机制相同，但**宿主能执行什么约束完全不同**。
这份文件把差异写清楚，只为一件事：**不让读者以为本形态拥有它没有的强制力**。

- 「能力」是宿主无关的（写账本 / 读文件 / 跑命令 / 派生子代理 / 发现工具 …）。
- 「工具真名」是宿主相关的：同一个能力在两个宿主下名字不同，**且一方的真名拿到另一方可能根本不存在**。
- 下面第三列的每个名字都来自本宿主自己的官方工具清单；第五列是**本宿主没有、或还没核实**的东西。

## 二、本形态的强制力现状（先说结论）

**只有声明，**未核实是否生效****。WorkBuddy/CodeBuddy 形态：插件 agent 的 disallowedTools 按官方文档受支持，但**运行时是否真的生效尚未实测**（三项运行时红测在 WB 侧待做）。故本形态下角色工具面只作为**声明**产出（生成一份角色工具面文档），不写进随包发布的 agent 定义——把没验的写成生效的，是本项目最贵的缺陷形状。实测回来翻转 hosts.codebuddy.enforcement 一处即可。

对比 DSH 形态：那边的角色工具面是**宿主强制**的——子代理的 deny 名单由宿主在挂载期编译，写错名字直接挂载失败（不是失败在第一次派工），
而且过滤作用于子代理继承到的整个工具面。本形态目前只有**声明**：下面第三节的名单是"应该封掉什么"，不是"已经封掉什么"。
