## 一、这份文件在回答什么

同一个编辑部有两个宿主形态：DSH（原生预设）与 WorkBuddy（本专家包）。两边人格相同、机制相同，但**宿主能执行什么约束完全不同**。
这份文件把差异写清楚，只为一件事：**不让读者以为本形态拥有它没有的强制力**。

- 「能力」是宿主无关的（写账本 / 读文件 / 跑命令 / 派生子代理 / 把没加载的工具翻出来 …）。
- 「工具真名」是宿主相关的：同一个能力在两个宿主下名字不同，**且一方的真名拿到另一方可能根本不存在**。
- 本宿主还要再按**形态**分一次：主编座位 / 团队成员 / 普通子代理三者的工具面实测不同，同一份名单在三种形态下不是同一件事。

## 二、本形态的强制力现状（先说结论）

**只有声明，未核实是否生效**。WorkBuddy/CodeBuddy 形态：**没有一条**机器强制——角色工具面只作为声明产出（生成一份文档），不写进随包发布的 agent 定义。两条理由：①插件 agent 的 disallowedTools 是否在运行时生效尚未实证（R-a 红测未跑）；②包内两个 agent 定义目前**都没有 frontmatter**，要声明必须先新建 frontmatter 块，而 agent 定义**不热加载、改完必须重启**，验证天然跨会话。把没验的写成生效的，是本项目最贵的缺陷形状。R-a 跑通后翻转 hosts.codebuddy.enforcement 并让装配器写 frontmatter。

对比 DSH 形态：那边的角色工具面是**宿主强制**的——子代理的 deny 名单由宿主在挂载期编译，写错名字直接挂载失败（不是失败在第一次派工），
而且过滤作用于子代理继承到的整个工具面。本形态目前只有**声明**：下面第三节的名单是"应该封掉什么"，不是"已经封掉什么"。

三种形态（映射的键，不是角色的属性）：

- **seat**：主编座位（专家组长本尊）——工具最全
- **teammate**：团队成员（本专家只有主笔是常驻成员）——实测缺 Edit/TaskStop 等、且缺 Agent/TeamCreate
- **subagent**：普通子代理（五个按需工种以派工提示词交给它跑）——实测缺 Agent/TeamCreate，但有 ToolSearch/DeferExecuteTool

### 连带影响（禁一条会顺带影响什么）

- `novel_event（档案员保留的那件）`：**粒度警告（2026-09-20 第三方实测）**：deny 只有**整工具**粒度，没有 op 级语法，宿主侧 disallowedTools 同样整名匹配 ⇒ 保留 novel_event ＝把 op=append（往事件带写）一并给它。原先文档写「保留 novel_event read」是把意图写成了事实，已改。要在硬面上只给读，只能改连接器侧——宿主层做不到（这也与本项目 REC-04 的结论同源：没有可机器验证的身份，就别在宿主层假装能按角色收权）。
- `DeferExecuteTool`：它同时是 Workflow 的执行器（宿主 DEFER_EXECUTE 会分派 WORKFLOW）⇒ deny 它可能**连带废掉 Workflow 面**。故不把 Workflow 与它合成一条能力：合成的后果是「看着只禁了发现，实际连编排一起禁」，而这种连带在名单里看不出来。
